# ADR-0002 — Curva: Ed25519 vs P-256

**Status:** Aceito provisoriamente (2026-11-13: dono do produto mandou seguir; recomendação adotada: P-256) · revisável

## Contexto
A chave de identidade, a atestação e as credenciais precisam de uma curva. Muitos *secure elements* (e FIDO/WebAuthn, e SD-JWT com `ES256`) suportam P-256; poucos suportam Ed25519. O firmware roda hoje em emulador, mas o alvo é MCU/SE (ADR-0012).

## Alternativas
| | Ed25519 | P-256 (ECDSA) |
|---|---|---|
| Suporte em SE/HW | Raro | Amplo |
| Assinatura | Determinística, simples, difícil de errar | ECDSA exige nonce seguro (RFC 6979 mitiga) |
| Ecossistema de credenciais (SD-JWT, WebAuthn, X.509) | Menor | Maior |
| Bibliotecas Rust | `ed25519-dalek` | `p256` |
| Prova ZK / BBS+ | — (BBS+ usa BLS12-381, outra curva de qualquer forma) | — |

## Recomendação
**P-256** para identidade e atestação, por compatibilidade com hardware seguro e com o ecossistema de credenciais. Ed25519 só se o hardware escolhido o suportar nativamente. Isolar atrás de um trait (`Signer`/`Verifier`) em `teko-crypto` para trocar sem reescrever o resto.

## Consequências
Exige cuidado com nonces (usar assinatura determinística RFC 6979). Curva de `Poseidon`/ZK é independente (campo da prova).
